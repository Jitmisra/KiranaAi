## 0. WHAT YOU ARE BUILDING, IN SIX LINES

A phone is clamped straight down 45–55 cm above an A3 printed mat (the **TAKHTI**) taped to an Indian kirana shop counter. The shopkeeper puts an item on the mat; its price paints onto the wood in perspective; he slides it toward the bag; the total climbs; he taps DONE; a real Razorpay UPI QR appears on the counter; the customer pays; the counter floods green **only when a signature-verified webhook confirms the exact amount landed.**

The pitch: *this shop has a perfect record of what it was **paid** and no record of what it **sold**. This is the missing column.*

Caption, never changes: **"It bills what leaves the shelf."**

## 1. NON-NEGOTIABLE INVARIANTS

Violating any of these is a stop-and-fix, not a tradeoff. Add a CI check for each one as you go.

1. **Money is integer paise.** A `float` anywhere in the money path fails the build. Write the lint on day 1.
2. **Green only on a verified webhook.** All four must hold: valid `X-Razorpay-Signature` HMAC-SHA256 over the **raw bytes before JSON parsing** ∧ event in the green set ∧ `notes.session_id` matches an open intent ∧ `amount == intent.amount_paise` exactly. Never green on mint, on render, on OCR, on a timer, or on optimism.
3. **Zero model weights ship to the browser.** Cold load stays under ~5 MB. The phone does geometry only. If a feature needs a model in the browser, the feature changes — not the invariant.
4. **The mask is applied at frame-grab, on the phone, before any pixel leaves the device.** The only buffer that survives the call is the rectified mat crop.
5. **`paisa` is a separate process, a different OS user, and the only holder of `RAZORPAY_KEY_SECRET` and `RAZORPAY_WEBHOOK_SECRET`.** It re-runs the crossing predicate server-side on submitted geometry before minting. A compromised phone must not be able to move a rupee.
6. **No forgery primitives.** Never write code that can construct or regenerate a UPI payload. The track disqualifies anything offence-capable and this is a public repo.
7. **Abstain rather than guess.** Unknown item → amber, excluded from the total. Stale ledger → amber, never red. No match → amber, never red. The system must never call a paying customer a liar while uncertain.
8. **Never use ngrok.** Razorpay hard-blacklists `ngrok.io`, `webhook.site`, `requestbin.com`, `beeceptor.com`, `hookbin.com`, `mockbin.org`, `loca.lt`, `localhost`, `.local`, `.internal`. Use `cloudflared`.
9. **Every number in the README is generated by `make bench`.** No number is typed by hand.

## 3. BUILD ORDER — money path before garnish

Do not start a stage until the previous stage's acceptance test passes.

**S1 — Skeleton.** `git init`. `docker-compose.yml` (postgres + `razorpay-mcp-server` **local**, because `close_qr_code` and `create_refund` are ❌ on the hosted remote — verified in `reference/razorpay-mcp-server/README.md:48`). Integer-paise `Paise` type + the float lint. Append-only audit log with the one-line schema from `PRD.md §4`. CI green.
→ **Accept:** `make test` passes on a clean clone.

**S2 — The plane.** ArUco `DICT_4X4_50` detect → `getPerspectiveTransform` → **840×1188 rectified buffer at 2.8283 px/mm** (note: 840/297 = 2√2; the PRD's "2 px/mm" is arithmetically wrong — use the real number). Mat-lock indicator: 4 markers ∧ mm/px error vs the printed 20 mm patch < 1.5% ∧ tilt < 8°.
→ **Accept:** reprojection RMSE assertion passes on synthetic and real frames.

**S3 — Placement + sell event.** `absdiff` vs a maintained empty-mat reference → `threshold` → `morphologyEx` → `findContours` → `minAreaRect` (**oriented**, not axis-aligned) → 5-frame stability gate. Directional exit via `supervision`-style `LineZone`, `minimum_crossing_threshold=3`. **Instrument the two uncounted-crossing counters** — `line_zone.py:170` returns silently when `tracker_id is None`, and a dropped track is an uncounted *sale*, i.e. a money bug wearing a vision bug's clothes.
→ **Accept:** 60 scripted placements, sell-event recall ≥ 0.98, uncounted crossings logged not swallowed.

**S4 — Money.** Mint on DONE. `paisa` re-runs the crossing predicate on submitted geometry. Webhook verify → green. Offline queue → AMBER PENDING. Poll fallback stamped `ledger_source: poll`.
→ **Accept:** a real end-to-end rupee, kill the network mid-flow, watch the queue drain, and `kill -9` mid-mint produces exactly one charge.

**S5 — Identity + enrollment.** MobileCLIP-S0 int8 (11.85 MB, `Xenova/mobileclip_s0`) on the brain via `onnxruntime` CPU, fired **only on a confirmed crossing (~0.5 Hz), never per frame.** Reject margin θ (top1−top2), φ (min similarity), τ (footprint tolerance). Warm enroll: unknown → amber → one tap on price → green forever. Collision guard at enroll time.
→ **Accept:** ≥250 held-out placements, published confusion matrix, amber rate ≤ 12%.

**S6 — The rescued four, cheapest first**, and only what the gates allowed: SAAF (0.5d) → CHILLA (1.25d) → IDENT (1.5d) → MUDRA (1.5d). **KHATA LIFT (4–5.5d) only if everything else is done and tested — it is the one that adds a genuinely new prop.**

## 4. THE LOOP — run this after every stage, and never skip it

```
1  BUILD      implement the smallest thing that could satisfy the acceptance test
2  TEST       run it. Not "read the code and reason about it" — RUN IT
3  MEASURE    write the actual number into results/. Not an estimate. The number
4  END-TO-END re-run every PREVIOUS stage's acceptance test. Regressions are the
              default outcome of new code, not the exception
5  IMPROVE    fix what the numbers say is worst, not what is most interesting
6  LOG        append to FAILURES.md if anything broke, with the date and the diagnosis
7  REPEAT     until the acceptance test passes twice in a row from a clean start
```

**Exit condition for the loop:** the stage's acceptance test passes **from a clean clone, twice**, and every earlier stage still passes.

**Anti-self-deception rules, because these are the ways this goes wrong:**
- Never report a test as passing that you did not run in this session.
- If a test is flaky, it is **failing**. Fix it or quarantine it loudly.
- If you cannot make something work, write it in `FAILURES.md` and move to the next stage. **Do not fake it, do not stub it and call it done, and do not quietly narrow the acceptance test to make it pass.**
- If you change an acceptance criterion, say so explicitly and say why.
- A number you did not measure does not go in the README.
